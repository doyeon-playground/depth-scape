# Internationalization

## Supported locales

| Locale | Language | Role |
| --- | --- | --- |
| `en` | English | Source and fallback |
| `ko` | Korean | Supported translation |
| `ja` | Japanese | Supported translation |
| `zh-CN` | Simplified Chinese | Supported translation |
| `es` | Spanish | Supported translation |

The first documentation release localizes the README. Product UI localization
will begin when user-facing application code is added.

## Principles

- English is the source of truth for technical and product documentation.
- Locale tags follow BCP 47 conventions.
- Missing translations fall back to English and must not break the interface.
- User-facing text must not be concatenated from translated fragments.
- Numbers, dates, file sizes, and plural forms use locale-aware formatters.
- Layouts must tolerate longer translations and different line-breaking rules.
- Error messages, accessibility labels, camera-limit notices, and
  generated-content disclosures are part of the translation surface.
- Model identifiers, artifact fields, commands, and locale tags remain unchanged.

## Planned application layout

The exact i18n library depends on the selected frontend framework. Locale data
should nevertheless follow a predictable shape:

```text
frontend/
`-- locales/
    |-- en.json
    |-- ko.json
    |-- ja.json
    |-- zh-CN.json
    `-- es.json
```

Use stable semantic keys instead of English sentences as keys:

```json
{
  "upload": {
    "title": "Choose a landscape photo",
    "unsupportedType": "Choose a JPG or PNG image."
  },
  "viewer": {
    "resetCamera": "Reset view",
    "showGeneratedRegions": "Show generated regions",
    "cameraLimitReached": "The view has reached its supported limit."
  }
}
```

## Locale selection

The initial application should:

1. honor a locale explicitly chosen by the user;
2. otherwise match a supported browser locale;
3. otherwise use English; and
4. persist the explicit choice locally without requiring an account.

Locale selection must not change depth, masks, generated content, camera
bounds, or artifact formats.

## Documentation workflow

1. Update the English source first.
2. Mark affected translations for review in the same pull request.
3. Preserve headings and relative links where practical.
4. Let a fluent reviewer check meaning, tone, and technical terminology.
5. Do not block a critical English correction solely because translations are
   pending; clearly label outdated translations instead.
